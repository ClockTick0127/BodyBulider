## 1. WebRTC 연결이 자주 실패하고 늦게 붙는다 👤👥

> **이 프로젝트 최고의 기술 스토리.** 내가 초기 구축한 영역이고, 실패 원인이 명확하고, 해결책이 정교하다.
> 면접에서 하나만 말해야 한다면 이것.

### 증상
4인이 로비에 모였을 때 일부 참가자의 영상이 안 뜨거나, 연결까지 수 초~수십 초가 걸렸다.
프로젝트 후반 내내 반복해서 터졌다 — 관련 커밋만 6개 이상:
`e9d334d`, `896674e`, `7b0837d`(2026-07-30) → `46b37bb`, `70fbf6b`, `8e26aa9`(2026-08-06~07)

### 원인
**재협상 경쟁 조건(renegotiation race condition).**

Mesh 구조에서 4명이 거의 동시에 로비에 들어오면, 양쪽이 서로에게 **동시에 offer를 보낸다**(glare).
초기 구현은 "상대가 offer를 받을 준비가 됐는지" 확인하는 단계 없이 곧바로 offer를 던졌기 때문에:

- 상대가 아직 `RTCPeerConnection`을 만들기 전에 offer가 도착 → 유실
- 이전 협상의 ICE candidate가 새 협상에 섞여 들어감 → 엉뚱한 연결 시도
- offer 재시도(`OFFER_RETRY_DELAYS_MS = [800, 1600, 3200]`)로 덮으려 했지만, **재시도는 원인이 아니라 증상을 늦출 뿐**이었다

### 해결
`961e06f`(BE) + `8e26aa9`(FE) 에서 **명시적 READY 핸드셰이크 + 세대(generation) 식별자**를 도입했다.

```
기존:  A ──offer──▶ B          (B가 준비됐는지 모름)

변경:  A ──READY──▶ B
       A ◀─READY_ACK── B      (양쪽 준비 확인 후에)
       A ──offer(generationId, negotiationId)──▶ B
```

핵심 변경 3가지:

1. **READY / READY_ACK 단계 추가** — offer를 보내기 전에 양쪽이 준비됐음을 확인.
   백엔드 `SignalingController`에 메시지 타입 추가, 프론트 `PeerManager`에 `handshakes` 맵 신설.
2. **`generationId`** — `PeerManager` 인스턴스마다 부여하는 UUID.
   상대가 새로고침·재입장하면 generationId가 바뀌므로, **이전 세션의 잔여 메시지를 구분해서 버릴 수 있다.**
3. **`negotiationId`** — 협상 시도마다 부여.
   ICE candidate 큐에 `{candidate, generationId, negotiationId}`로 함께 저장해,
   **협상 세대가 다른 candidate가 섞이지 않도록** 했다.

재시도 전략도 offer 재시도에서 READY 재시도(`[500, 1000, 2000, 4000]`)로 옮겼다.
**연결 자체가 아니라 준비 확인을 재시도하게 바꾼 것**이 요점이다.

### 배운 것
- **P2P는 "양쪽이 동시에 움직이는" 시스템**이다. 한쪽 관점으로만 짠 코드는 반드시 경쟁 조건을 만든다.
- 재시도로 덮이는 버그는 대개 **상태 기계가 빠진 것**이다. 재시도 딜레이를 늘리고 있다면 설계를 의심해야 한다.
- 분산 시스템에서 **세대 식별자(generation/epoch)로 낡은 메시지를 버리는 패턴**은 일반적인 기법이다.
  (Raft의 term, Kafka의 epoch와 같은 발상)

> ✍️ 채우기: 이 문제를 어떻게 재현하고 디버깅했나?
> `chrome://webrtc-internals`를 봤나? 4명 동시 접속을 어떻게 테스트했나 (창 4개? 팀원 소집?)
> → **재현 방법**을 말할 수 있으면 신뢰도가 크게 오른다.

## 2. Redis 세션 직렬화를 JSON으로 바꿨더니 인증이 깨졌다 👥

### 증상
Redis 세션 직렬화를 JDK → JSON으로 전환하자(`37cc75d`, 2026-08-06) **로그인 로직이 파손**됐고,
같은 날 후속 수정이 필요했다(`6680823`).

### 원인
JDK 직렬화는 자바 객체 타입 정보를 통째로 보존하지만, JSON은 그렇지 않다.
세션에 담긴 인증 객체가 역직렬화될 때 원래 타입으로 복원되지 않아 인증 로직이 이를 인식하지 못했다.

### 해결
JSON 직렬화 설정에서 타입 정보를 보존하도록 조정하고, 테스트를 보정했다.

### 배운 것
- **직렬화 방식 변경은 저장 포맷 변경이다.** 코드 한 줄이 아니라 데이터 계약이 바뀐다.
- 그럼에도 JSON으로 간 건 옳았다: JDK 직렬화는 클래스가 바뀌면 기존 세션이 전부 깨지고,
  저장된 내용을 사람이 읽을 수 없어 디버깅이 불가능하다.

> ⚠️ **백엔드 팀원(백화진) 작업이다.** "제가 했습니다"라고 말하면 안 된다.
> "팀에서 이런 이슈가 있었고, 원인은 ~였습니다"로 말한다.

## 3. 물리 시뮬레이션 — 캐릭터가 지형을 뚫고 벽을 탄다 👥

### 증상
- 캐릭터가 빠르게 움직일 때 지형을 **관통**(터널링) — `81cad21` "고속 이동 판정 안정성 개선"
- 캐릭터가 **수직 벽을 타고 올라감** — `1d94168`
- 지형의 **미세한 턱에 걸림** — `8b7ff57`
- 다리 꺾이는 지점에 **경계 틈새** 발생 — `6d63a41`

### 원인
이산 시간 물리 시뮬레이션의 전형적 문제. 물리 스텝(1/180초) 사이에 물체가 충돌체를 통과할 만큼 이동하면
그 사이의 충돌이 감지되지 않는다.
플레이어의 팔로 만든 지형은 **매 라운드 모양이 달라지는 임의의 선분 집합**이라 예외 케이스가 훨씬 많았다.

### 배운 것
- **게임 물리는 "정확한 계산"이 아니라 "납득 가능한 결과"를 목표로 한다.**
  물리적으로 정확해도 플레이어가 이상하다고 느끼면 버그다.
- 사용자가 지형을 직접 만드는 게임은 **입력 공간이 사실상 무한**하다. 테스트로 다 못 덮는다.

> ⚠️ 백엔드 팀원 작업. 자세한 알고리즘은 모르므로 면접에서 깊이 들어가지 말 것.
> ✍️ 다만 프론트에서 이 결과를 렌더링하는 쪽 문제(`08f1171` 카메라 스무딩 제거,
> `46b37bb` 오리 캐릭터 떨림)는 프론트 영역이니 확인해서 적을 것.

## 4. 포즈 관절이 떨리고, 가려지면 다리가 찢어진다 👤

> **내가 단독으로 잡은 문제.** `resolvePosePoints.ts` 136줄 중 89줄(65%)이 내 코드다.
> 1번(WebRTC)이 팀과 함께 푼 문제라면, **이건 온전히 내 것**이라 면접에서 짝으로 쓰기 좋다.
> 커밋 3개(`81fcba3`, `d63063a`, `0cf044f`)에 걸쳐 **한 번 실패하고 되돌린 뒤 다시 푼** 과정이 남아 있다.

### 배경 — 왜 이게 치명적인가
플레이어의 팔 관절 6개(양쪽 손목–팔꿈치–어깨)가 **그대로 게임 지형이 된다.**
일반적인 모션 앱이라면 관절이 조금 떨려도 그림이 흔들릴 뿐이지만, 이 게임에서는
**떨리는 관절 = 떨리는 지형**이고, 그 위를 캐릭터가 굴러간다. 인식 품질이 곧 게임 물리다.

또 서버 계약이 **항상 6개 좌표**를 요구한다. 관절 하나가 안 잡혀도 6개를 채워 보내야 한다.
**"못 잡은 관절에 무슨 값을 넣을 것인가"** 가 이 문제의 전부였다.

### 증상
- 가만히 있어도 관절이 미세하게 떨림 → 지형이 진동
- 손목이 화면 밖으로 나가거나 몸에 가려지면 **다리가 엉뚱한 곳으로 튐**
- 조명·거리에 따라 인식이 자주 끊김

### 시도 1 — 실패 (`81fcba3`, 08-03 17:15)
세 가지를 한꺼번에 넣었다.

1. **인식 신뢰도 임계값 완화**: `0.5 → 0.35` (세 값 모두). 인식이 덜 끊기게.
2. **속도 적응형 EMA 스무딩**: 지수 이동 평균으로 떨림을 잡되, 알파를 고정하지 않고 움직임 속도로 분기.
   ```
   프레임 간 이동거리² > 0.0016 (화면 폭 4%)  →  alpha 0.95  (빠른 동작: 지연 없이 즉시 추종)
   그 이하 (정지/느린 동작)                    →  alpha 0.70  (떨림 제거)
   ```
3. **가려짐 프레임 카운팅**: 관절별로 연속 미인식 횟수를 세서, 5프레임(≈0.15초) 미만이면 이전 좌표를 유지하고,
   그 이상이면 `[0, 0]`으로 초기화해 "완전히 제외".

**3번이 더 나쁜 버그를 만들었다.**

### 되돌림 — 22분 뒤 (`d63063a`, 08-03 17:37)
문제는 단순하고 뼈아팠다. **`[0, 0]`은 "값 없음"이 아니라 "화면 좌상단"이다.**

관절을 제외하려고 넣은 `[0,0]`이 서버에는 **좌상단 모서리에 있는 유효한 관절**로 전달됐고,
지형이 화면 좌상단까지 쭉 이어지며 **다리가 찢어졌다**. 당시 코드에 남긴 주석 그대로:

> `// 이전 유효 좌표가 존재하면 유지 (화면 좌상단 0,0으로 찢어지는 왜곡 방지)`

프레임 카운팅과 `[0,0]` 초기화를 걷어내고, **이전 유효 좌표를 무기한 유지**하는 방식으로 되돌렸다.
EMA 스무딩(2번)은 효과가 있었으므로 남겼다. `GamePage`에서 인식 실패 시 6개를 `[0,0]`으로 채우던 코드도 함께 제거했다.

### 시도 2 — 해결 (`0cf044f`, 08-04)
다음 날 원인을 나눠서 다시 접근했다. **"떨림"과 "미인식"은 다른 문제인데 한꺼번에 풀려고 했던 게 실패 원인**이었다.

**(a) 인식률 자체를 올린다 — 모델 교체**
`pose_landmarker_lite` → **`pose_landmarker_full`**. 임계값을 낮춰 억지로 인식을 늘리는 대신,
더 무거운 모델로 인식 품질을 올리는 쪽을 택했다. (추론 비용 ↑ 를 감수)

**(b) 신뢰도 임계값을 역할별로 분리**
시도 1에서 세 값을 다 `0.35`로 뭉갠 게 잘못이었다. 셋은 역할이 다르다.
```
minPoseDetectionConfidence : 0.35   최초 검출 — 낮춰서 일단 사람을 잡는다
minPosePresenceConfidence  : 0.7    존재 판정 — 높여서 헛것을 안 잡는다
minTrackingConfidence      : 0.5    추적 유지 — 중간
```
동시에 이 값들을 `usePoseLandmarker`의 옵션으로 주입 가능하게 바꿔, **실험할 수 있게** 만들었다.

**(c) 결측 관절 처리 원칙을 확정**
```
이전 유효 좌표가 있으면  →  그 값을 유지 (freeze)
없으면                   →  [0, 0]  (최초 프레임뿐, 지형이 아직 없으므로 안전)
```
시도 1에 있던 **"인접 관절로 대체"** 로직은 완전히 제거했다.
손목이 안 잡힐 때 팔꿈치 좌표를 대신 쓰면 통계적으로는 그럴듯해 보이지만,
게임에서는 **손목이 팔꿈치로 순간이동 = 다리 길이가 갑자기 줄어드는** 것이라 오히려 더 이상했다.

**(d) `resolveTrackedJoints` 추가** — 관절 객체 단위로도 같은 freeze 전략을 적용해, 렌더링 쪽에서 다리가 사라지는 현상을 막았다.

**(e) 디버깅 전용 라우트 개설** — `/pose-test`, `/dev/mediapipe` (`App.tsx`).
게임을 처음부터 돌리지 않고 포즈 인식만 따로 띄워서 튜닝할 수 있게 만들었다.
**이걸 시도 1 전에 만들었다면 22분짜리 실패를 안 했을 것이다.**

### 최종 값 (현재 master)
| 항목 | 값 |
| --- | --- |
| 모델 | `pose_landmarker_full` (float16) |
| detection / presence / tracking | 0.35 / 0.7 / 0.5 |
| EMA 알파 (정지·느림) | 0.65 |
| EMA 알파 (빠른 동작) | 0.95 |
| 빠른 동작 임계값 | 이동거리² > 0.0016 (화면 폭 ≈4%) |
| 결측 관절 | 이전 유효 좌표 유지, 없으면 `[0,0]` |

### 배운 것
- **센티널 값이 좌표계 안의 유효한 점이면 센티널이 아니다.** `[0,0]`으로 "없음"을 표현했는데
  받는 쪽에는 "좌상단에 관절이 있음"으로 읽혔다. 없음을 표현하려면 `null`이거나, 별도 유효성 플래그여야 한다.
  → 이 교훈은 좌표뿐 아니라 `-1`, `0`, 빈 문자열을 "없음"으로 쓰는 모든 경우에 적용된다.
- **결측치를 무엇으로 채울지는 도메인이 정한다.** 인접 값 보간은 일반적으로 합리적이지만,
  이 도메인에서는 "관절이 순간이동한다"는 뜻이라 틀린 선택이었다.
- **떨림과 지연은 트레이드오프**다. 스무딩을 세게 걸면 안 떨리지만 굼뜨다.
  하나의 상수로 둘 다 만족시킬 수 없어서, **움직임 속도로 분기**해 두 목표를 나눴다.
- **세 개를 한 번에 바꾸면 뭐가 효과였는지 모른다.** 시도 1에서 임계값·스무딩·가려짐 처리를 동시에 넣었고,
  결과가 나빠졌을 때 원인을 분리하는 데 시간을 썼다. 시도 2에서는 나눠서 접근했다.
- **22분 만에 되돌린 건 잘한 판단이다.** 내가 방금 쓴 코드를 지우는 게 아까워서 붙잡고 있었다면 더 나빠졌다.

#### a. 6점 연결 순서가 틀려 있었다 (`1804205`, 07-31) — **가장 중요**

이건 "좌표가 조금 어긋난" 문제가 아니라 **지형의 형태 자체가 틀린** 문제였다.

```
기존 배열:  [leftShoulder, leftElbow, leftWrist, rightShoulder, rightElbow, rightWrist]
기존 세그먼트: [0,1] [1,2] [0,3] [3,4] [4,5]
   → 어깨에서 손목으로 바깥으로 뻗는 두 갈래 + 어깨끼리 연결.
     다리(bridge)가 아니라 갈라진 모양이 된다.

변경 배열:  [leftWrist, leftElbow, leftShoulder, rightShoulder, rightElbow, rightWrist]
변경 세그먼트: [0,1] [1,2] [2,3] [3,4] [4,5]
   → 왼손목에서 오른손목까지 끊기지 않는 하나의 폴리라인. 이게 진짜 "다리"다.
```

`posePointOrder.ts`를 신설하면서 주석에 **"포즈 촬영 · 맵 렌더링 · 게임 서버가 공유하는 인덱스 계약"** 이라고 못박고 테스트를 붙였다. 흩어져 있던 배열 리터럴을 한 곳으로 모은 것이다.

> 💡 **내 작업과의 연결 — 이 연결을 말할 수 있으면 좋다.**
> 내가 시도 1에 넣었던 **"인접 관절로 대체"** 폴백(`current[index±1]`)은
> **배열이 연속된 사슬일 때만 의미가 있다.** 이 커밋 이전 순서였다면 인덱스 ±1이 실제 인접 관절이 아니었다.
> 결과적으로 내가 그 폴백을 제거한 판단(시도 2-c)은 이 계약이 정리된 뒤에야 제대로 평가할 수 있었던 셈이다.

#### b. 첫 게임 시작 시 인식 실패 (`fcb9d21`, 08-04)

**원인**: 게임 페이지에 진입한 *뒤에야* MediaPipe WASM + `.task` 모델(수 MB) 다운로드와 GPU 초기화가 시작됐다.
첫 촬영 턴이 그보다 먼저 와서 인식이 안 됐다.

**해결**: `preloadGame.ts` 신설 — **로비에서 미리 다 끝낸다.**
1. 게임 화면 코드 청크를 `import()`로 선로딩
2. 맵·캐릭터 스프라이트·효과음 8개·컷신을 `fetch`로 브라우저 캐시에 적재
3. MediaPipe 런타임 생성 + **GPU 워밍업**

워밍업이 영리하다 (`poseLandmarkerRuntime.ts`):
```ts
runningMode: 'IMAGE'  로 생성
  → 64×64 빈 캔버스에 detect() 1회   // GPU 셰이더 컴파일을 미리 유발
  → setOptions({ runningMode: 'VIDEO' })  로 전환
```
그리고 런타임을 모듈 레벨 싱글턴으로 캐시해 **로비 → 게임 페이지 이동 간에 그대로 물려준다**
(`Retain one warmed runtime across LobbyPage -> GamePage navigation`).
진행률(`code → assets → ai → ready`)을 로비 UI에 표시해 대기 시간을 체감상 숨겼다.

**배운 것**: 무거운 초기화는 **사용자가 어차피 기다리는 화면**으로 옮긴다.
"빠르게 만든다"가 안 되면 "기다림을 이미 기다리는 곳에 숨긴다"가 차선이다.

> 💡 **내 리팩터링이 이 작업을 가능하게 했다 — 시각이 증거다.**
> | 시각 | 커밋 | 내용 |
> | --- | --- | --- |
> | 08-04 **14:34** | `0cf044f` (나) | 모델 경로·신뢰도를 하드코딩에서 빼내 **옵션으로 주입 가능하게** 하고 `DEFAULT_CONFIDENCE` export |
> | 08-04 **14:53** | `fcb9d21` (백성수) | 그 `DEFAULT_CONFIDENCE`와 `DEFAULT_POSE_MODEL_PATH`를 **그대로 import해서** 프리로드 구현 |

> 하드코딩된 채였다면 런타임 생성 로직을 훅 밖으로 꺼낼 수 없었을 것이다.
>

> "설정을 주입 가능하게 바꿨더니 팀원이 그 위에 프리로드를 얹을 수 있었습니다" —
> 추상적인 '협업했다'보다 훨씬 구체적이고, 커밋 시각으로 검증 가능하다.

#### c. 다음 라운드 첫 플레이어 인식 불가 (`aa58c1c`, 07-30)

**원인**: 포즈 추출용 `videoRef`가 **단일 ref**였고, `isMe && (isCurrent || firstMySlotNo === slotNo)`라는
조건부로 특정 슬롯의 `<video>`에만 붙였다. 라운드가 넘어가 차례가 바뀌면 ref가 엉뚱한 엘리먼트를 가리키거나 비었다.

**해결**: 슬롯 번호 → `<video>` 의 `Map`(`videoBySlotRef`)으로 바꾸고 **콜백 ref**로 등록.
`captureLatestPose()`가 video를 인자로 받도록 시그니처를 바꾸고, effect 의존성에 `currentPlayer`를 추가했다.

**배운 것**: **React ref를 조건부로 옮겨 붙이면 생명주기가 꼬인다.**
"지금 누가 쓰는가"가 바뀌는 값이라면 ref 하나를 옮기지 말고, 전부 등록해두고 골라 쓰는 게 맞다.

#### d. 영상과 스켈레톤 좌표 어긋남 (`880d310`, 07-30)

CSS 두 줄이다. 카메라 뷰포트 `aspect-ratio: 4/3 → 230/180`, 폭 `32cqi → 25cqi`.

**원인**: `<video>`와 포즈 `<canvas>`가 `object-fit: cover`로 그려지는데,
컨테이너 비율이 실제 웹캠 스트림 비율과 달라 **크롭**이 발생했다.
스켈레톤은 원본 프레임 좌표계로 그리므로, 화면에 보이는 영상과 선이 어긋났다.

**배운 것**: `object-fit: cover`는 **보이는 것과 좌표계를 어긋나게 만든다.**
영상 위에 좌표 기반 오버레이를 그릴 거면 컨테이너 비율을 소스 비율에 맞추거나, 크롭량만큼 좌표를 변환해야 한다.

#### e. HiDPI에서 스테이지가 잘림 (`e4f2292`, 07-31)

**원인**: `.ingame-page { height: 100% }` → `.game-board { height: 100%; max-height: 900px }` 로 이어지는
**퍼센트 높이 체인**. 디스플레이 배율이 높으면 논리 뷰포트 높이가 줄어드는데, 그 환경에서 정사각 보드가 잘렸다.

**해결**: `height: 100svh`로 바꾸고, 보드 크기를 컨테이너 쿼리로 **가로세로 중 작은 쪽**에 맞췄다.
```css
.game-board-viewport { container-type: size; }
.game-board { width: min(100cqw - 12px, 100cqh - 12px, 860px); height: 동일; }
```
여기에 `@media (max-height: 760px / 640px)`로 헤더·사이드바·카메라 높이를 단계적으로 축소했다.

**배운 것**: **HiDPI(디스플레이 배율)는 논리 뷰포트를 작게 만든다.** 해상도가 높다고 공간이 넓은 게 아니다.
정사각형을 화면에 맞추려면 퍼센트 높이 체인보다 `min(cqw, cqh)`가 안전하다.

#### f. 카메라가 캐릭터를 못 따라감 (`08f1171`, 08-05)

CSS 한 줄. `transition-duration: 180ms` → `transition: none`.

**원인**: 캐릭터 추적 카메라를 CSS `transform` + 180ms 트랜지션으로 부드럽게 만들었는데,
시뮬레이션 프레임이 그보다 자주 갱신됐다. **트랜지션이 끝나기 전에 다음 목표로 갱신** 되니
카메라는 늘 보간 중이었고, 영원히 캐릭터를 따라잡지 못했다.

> 💡 **내 작업과의 대비 — 면접에서 헷갈리지 말 것.**
> | | 대상 | 방향 | 목적 |
> | --- | --- | --- | --- |
> | 내 작업 (4번) | 관절 좌표 | 스무딩을 **넣음** (EMA) | 떨림 제거 |
> | 이 커밋 | 카메라 transform | 스무딩을 **뺌** (CSS transition) | 지연 제거 |
>
> 같은 "스무딩"이지만 대상도 방향도 반대다. 그리고 내 EMA가 이 함정을 피한 이유가 있다 —
> **속도가 빠를 때 알파를 0.95로 올려** 사실상 스무딩을 끄기 때문이다.
> 고정 보간이었다면 나도 똑같이 뒤처졌을 것이다. 이 대비를 말할 수 있으면 설계 의도를 이해하고 있다는 증거가 된다.

## 5. 보안 취약점 — STOMP 도청 및 신원 위조 👥

### 증상 (팀 내부 점검에서 발견)
- 다른 방의 STOMP 토픽을 **구독하면 게임 내용을 도청**할 수 있었다 — `e6c1257`
- WebRTC 시그널링 메시지의 **`senderId`를 위조**할 수 있었다 — `b940f7f`, `4e3586b`
- 방에 참여하지 않은 사용자가 방 정보를 조회할 수 있었다 — `8e25e89`
- 코드로 참여하면 **이미 진행 중인 방에 난입** 가능 — `8c9699e`
- 잠긴(비밀번호) 방에 **quick join으로 우회 입장** 가능 — `8b29427`

### 원인
공통 원인 하나다. **클라이언트가 보낸 값을 그대로 믿었다.**
`senderId`를 페이로드에서 읽고, 구독 경로 권한을 검사하지 않았다.

### 해결
STOMP 세션의 인증 정보에서 신원을 꺼내 쓰도록 바꾸고(페이로드 값 무시),
SUBSCRIBE 시점에 해당 방 참여자인지 검증하는 인터셉터를 넣었다.

### 배운 것
- **WebSocket은 REST보다 인증을 잊기 쉽다.** REST는 요청마다 필터를 타지만,
  WebSocket은 연결 시 한 번 인증하고 나면 이후 메시지가 무방비가 되기 쉽다.
- "클라이언트 입력을 믿지 않는다"는 원칙이 **실시간 통신에서도 똑같이 적용된다**는 걸 실제 사례로 봤다.

> ⚠️ 백엔드 팀원(백화진) 작업. 다만 시그널링은 내가 만든 WebRTC와 맞닿아 있어서
> "제 초기 구현에는 senderId 검증이 없었고, 팀원이 보안 점검에서 이를 발견해 보완했습니다"라고
> **내 몫을 인정하며 말하는 게 정확하고, 오히려 인상이 좋다.**
