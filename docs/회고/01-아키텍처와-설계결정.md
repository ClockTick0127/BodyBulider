# 아키텍처와 설계 결정

레포 `README.md` 6번에 **구조가 무엇인지**는 이미 적혀 있다. 여기 적는 건 **왜 그 구조인지**다.
면접에서 나오는 질문은 항상 "왜"쪽이다.

---

## 전체 그림

```text
Layer 1  Client      브라우저
                       ├─ MediaPipe Pose  (온디바이스 추론)
                       └─ WebRTC Mesh P2P (영상·음성)
Layer 2  Gateway     Nginx — SSL Termination, Reverse Proxy
Layer 3  Frontend    React 19 + Vite (정적 서빙)
Layer 4  Backend     Spring Boot 3.5
                       ├─ REST API
                       ├─ STOMP WebSocket (게임 메시지 · 방 상태 · WebRTC 시그널링)
                       └─ dyn4j        (서버 권위 물리 시뮬레이션)
Layer 5  Storage     MySQL 8.4 (영속)  ·  Valkey (세션 · 게임 세션 캐시)
```

핵심은 **데이터가 두 갈래로 흐른다**는 점이다.

- **게임 데이터**는 반드시 서버를 경유한다 (포즈 좌표 → 서버 → 시뮬레이션 → 결과 프레임 브로드캐스트)
- **영상·음성**은 서버를 안 거치고 P2P로 직접 간다 (WebRTC Mesh)

이 분리가 이 프로젝트 설계의 뼈대다. 하나로 통일하지 않은 이유가 아래 결정 1, 3에 있다.

---

## 결정 1. 물리 연산을 클라이언트가 아니라 서버가 한다

### 결정
포즈 좌표만 클라이언트가 보내고, **물리 시뮬레이션은 서버(dyn4j)가 전담**한다.
클라이언트는 계산된 결과 프레임을 받아 재생만 한다.

### 대안
- (A) 각 클라이언트가 각자 물리 계산 → 서버는 좌표만 중계
- (B) 방장 클라이언트가 계산 → 나머지에 브로드캐스트 (호스트 권위)
- (C) **서버가 계산 → 전원에게 브로드캐스트 (채택)**

### 근거
협동 게임에서 **"내 화면에선 성공했는데 쟤 화면에선 실패"가 나오면 게임이 성립하지 않는다.**
물리 시뮬레이션은 부동소수점 연산이라 브라우저·기기별로 결과가 미세하게 갈린다.
(A)는 이 발산을 막을 방법이 없고, (B)는 방장 기기 성능에 게임 결과가 좌우되고 방장이 나가면 무너진다.

(C)는 단일 진실 공급원(single source of truth)이 하나뿐이라 결과가 항상 일치한다.
심판이 한 명이어야 경기가 성립하는 것과 같다.

### 트레이드오프 (감수한 것)
- **입력 지연**: 포즈를 보내고 결과를 받기까지 왕복 지연이 생긴다.
  → 이 게임은 실시간 반응 게임이 아니라 **"3초 촬영 → 시뮬레이션 관람"** 턴제 구조라서 지연이 게임성을 해치지 않는다.
    구조가 지연을 감당할 수 있게 게임 규칙 자체를 설계한 셈이다.
- **서버 부하**: 방마다 물리 엔진을 돌려야 한다. 시뮬레이션을 최대 15초, 물리 스텝 1/180초로 제한해 상한을 뒀다.

> ✍️ 이 결정을 팀에서 언제, 어떤 논의 끝에 내렸는지 기억나면 적기.
> (처음부터 서버 권위였나? 클라 계산으로 갔다가 결과 불일치를 겪고 바꿨나?
>  후자라면 그게 훨씬 좋은 면접 스토리다.)

## 결정 2. 포즈 추론을 서버가 아니라 브라우저에서 한다

### 결정
MediaPipe Pose Landmarker(Lite, GPU delegate)를 **브라우저 안에서** 구동한다.
서버로는 추론 결과인 관절 좌표 6개만 보낸다.

### 대안
- (A) 웹캠 영상을 서버로 스트리밍 → 서버가 추론
- (B) **브라우저 온디바이스 추론 → 좌표만 전송 (채택)**

### 근거
- **대역폭**: 영상 스트림 대신 관절 좌표 6쌍만 보내면 된다. 차이가 수천 배다.
- **프라이버시**: 웹캠 원본 영상이 서버에 올라가지 않는다.
- **서버 비용**: 서버에서 ML 추론을 돌리려면 GPU 인스턴스가 필요하다. EC2 예산으로 불가능.
- **접근성**: 프로젝트 기획 자체가 "별도 장비 없이 웹캠만으로"였다. 브라우저 완결성이 기획과 맞았다.

### 트레이드오프
- 추론 품질이 **사용자 기기 성능에 의존**한다. 저사양 기기에서 프레임이 떨어진다.
- 조명·배경 등 환경에 따라 인식률이 갈린다. → 실제로 문제가 됐다. [03-트러블슈팅.md](03-트러블슈팅.md) 참고.

## 결정 3. 화상통화를 SFU가 아니라 WebRTC Mesh로

### 결정
플레이어끼리 **직접 P2P 연결(Mesh)** 한다. 미디어 서버를 두지 않는다.

### 대안
- (A) SFU (mediasoup, Janus, LiveKit 등) — 미디어 서버가 중계
- (B) MCU — 서버가 합성해서 단일 스트림 송출
- (C) **Mesh P2P (채택)**

### 근거
**방 정원이 최대 4명**이라는 게 결정적이었다.
Mesh는 N명이면 각자가 N-1개 연결을 유지해야 해서 연결 수가 N²로 늘어난다.
4명이면 1인당 3개 연결 — 일반 가정용 업링크로 충분히 감당된다.

반면 SFU를 도입하면 미디어 서버 운영·배포·스케일링이 통째로 추가된다.
**3주짜리 프로젝트에서 그건 게임을 못 만들게 되는 선택**이었다.

### 트레이드오프
- **확장 불가**: 4명이 상한이다. 8명만 돼도 1인당 7개 연결이라 무너진다.
  → 정원을 4명으로 고정한 게임 기획과 맞물려 있어서 당장은 문제가 아니지만, **구조적 한계인 건 맞다.**
    면접에서 "인원을 늘리려면?"이라고 물으면 SFU 전환이 정답이고, 그걸 안 한 이유가 위 근거다.
- NAT 뒤 사용자를 위해 TURN 서버가 필요하다. 환경변수(`VITE_TURN_*`)로 구성 가능하게 열어뒀고,
  미설정 시 Google STUN만 사용한다. → **대칭형 NAT 환경에서는 연결 실패 가능성이 남아 있다.**

### 시그널링은 별도 서버 없이 STOMP에 얹었다
이미 게임 메시지용 STOMP WebSocket이 있었으므로, SDP/ICE 교환도 같은 채널을 썼다
(`/app/signal/offer`, `/answer`, `/candidate`, 후에 `/ready` 추가).
**인프라를 하나도 늘리지 않고 시그널링을 해결한 것**이 이 설계의 실질적인 이득이었다.

## 결정 4. 게임 메시지를 코드 기반으로

### 결정
STOMP 게임 메시지를 문자열 타입이 아니라 **숫자 코드**로 정의했다.
`100` START, `102` CAPTURING, `104` SIMULATING, `106` RESULT, `107` POSE_BROADCAST …

### 근거
- 포즈 브로드캐스트(`107`)는 **촬영 중 초당 수십 번** 오간다. 페이로드를 줄일 이유가 충분했다.
- 코드 번호대를 나누면(100번대 게임 흐름 등) 메시지 분류가 구조적으로 드러난다.

### 트레이드오프
- **가독성이 나쁘다.** `104`가 뭔지 알려면 문서나 상수 정의를 봐야 한다.
  → 프론트/백 양쪽에 상수를 두어 완화했지만, **양쪽 정의가 어긋날 위험이 구조적으로 남는다.**
    지금 다시 한다면 스키마를 한 곳에서 정의하고 양쪽으로 생성하는 방식을 고려하겠다.

## 결정 5. 인증을 JWT가 아니라 세션 쿠키로

### 결정
세션 쿠키 기반 인증. 세션 저장소는 Valkey(Redis).

### 이력 (실제로 두 번 바뀌었다)
1. 초기: **JWT** → 2026-07-21 세션 방식으로 전환 (`abf9c56`)
2. 세션을 **서버 인메모리**에 보관 → 2026-08-04 **Redis로 이관** (`798be71`)
3. Redis 직렬화를 **JDK → JSON** 으로 전환 (`37cc75d`), 이때 인증 로직이 깨져서 후속 수정 (`6680823`)

### 근거
- **JWT → 세션**: WebSocket(STOMP) 연결에서 인증을 다뤄야 했는데, 세션 쿠키가 핸드셰이크에 자연스럽게 실린다.
  또 게임 중 강제 로그아웃/세션 무효화가 필요한데 JWT는 무효화가 어렵다.
- **인메모리 → Redis**: 서버 재시작 시 전원 로그아웃되는 문제, 그리고 다중 인스턴스 확장 대비.
- **JDK → JSON 직렬화**: JDK 직렬화는 클래스 구조가 바뀌면 역직렬화가 깨지고, 저장 내용을 사람이 볼 수 없다.

> 💡 **이 항목은 면접용으로 가치가 높다.**
> "처음부터 잘 만든 것"보다 **"문제를 만나서 두 번 바꾼 것"**이 훨씬 좋은 이야기다.
> 특히 3번 — 직렬화 방식을 바꿨더니 인증이 깨졌고, 그걸 잡은 과정 — 은
> "변경의 파급 범위를 예측 못 했다"는 솔직한 교훈까지 붙일 수 있다.
> 다만 **이건 백엔드 팀원 작업이다.** 내 것처럼 말하면 안 되고, "팀에서 이런 일이 있었고 나는 이렇게 이해했다"로 말한다.
