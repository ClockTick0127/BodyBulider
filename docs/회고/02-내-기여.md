## 1. WebRTC 화상통화 — 초기 설계 및 구축

### 무엇을 했나
프로젝트에 **화상통화가 아예 없던 시점(2026-07-23)에 전체 구조를 설계하고 처음 구현**했다.
단일 커밋 `09cbe96`으로 11개 파일 683줄이 추가됐고, 그때 만든 파일 구성이 프로젝트 끝까지 유지됐다.

```
frontend/src/features/webrtc/
├─ hooks/useWebRTC.ts          연결 생명주기를 React에 연결
├─ services/peerManager.ts     RTCPeerConnection 다중 관리 (Mesh)
├─ services/mediaManager.ts    getUserMedia, 트랙 on/off, 장치 전환
├─ services/webrtcConfig.ts    ICE 서버 (STUN/TURN) 설정
└─ components/VideoGrid.tsx    참가자 영상 그리드
```

같은 커밋에서 시그널링을 별도 서버 없이 기존 STOMP 소켓에 얹었다
(`roomSocket.ts` 106줄 수정 — offer/answer/candidate 송수신 추가).
**인프라를 늘리지 않고 시그널링을 해결한 것**이 이 작업의 핵심 판단이었다.

### 정직한 소유권
최종 코드 기준 `peerManager.ts` 522줄 중 내 줄은 73줄(14%)이다.
프로젝트 후반에 연결 안정성 문제가 계속 터지면서 **팀원(백성수)이 대폭 재작성**했다
— 재협상 경쟁 조건 대응, generationId/negotiationId 도입, READY 핸드셰이크 등
([03-트러블슈팅.md](03-트러블슈팅.md) 1번).

`useWebRTC.ts`는 230줄 중 101줄(44%)이 남아 있고, `mediaManager.ts`는 73줄(76%)로 내가 계속 주 작성자였다.

> 💡 **이걸 어떻게 말할 것인가**
> 숨기면 안 된다. 오히려 좋은 소재다:
> "초기 구현은 정상 시나리오만 고려한 offer/answer 교환이었습니다.
>  실제 4인 동시 접속 테스트에서 연결이 자주 실패했고, 원인이 재협상 경쟁 조건이라는 걸

> → **자기 코드가 대체된 걸 인정하면서 이유를 정확히 설명하는 것**이,
>    안 터진 척하는 것보다 훨씬 신뢰를 준다. 실제로 그게 팀 개발이다.

## 2. 미디어 장치 설정 시스템 (사실상 단독)

### 무엇을 했나
`SettingsModal` — 마이크/카메라 **장치 선택**, 입출력 **음량 조절**, 장치 미리보기.
`9ac76ad`(최초 245줄) → `6890762`, `cd793c0`, `1ef4bac`, `3a6ed4b` 로 이어지며 완성.

최종 `SettingsModal.tsx` 236줄 중 **231줄(98%)** 이 내 코드다. CSS 157줄도 내가 썼다.

### 왜 필요했나
웹캠 게임이라 **장치가 안 잡히면 게임 자체가 성립하지 않는다.**
노트북 내장 캠 + 외장 웹캠처럼 장치가 여러 개인 환경에서 브라우저 기본 선택이 틀리는 경우가 흔했고,
이걸 사용자가 직접 고를 수 있어야 했다.

WebRTC로 이미 나가고 있는 스트림을 끊지 않고 **장치를 교체**해야 해서
`mediaManager`의 트랙 교체 로직과 함께 설계했다.

> ✍️ 여기 채우기: `enumerateDevices()` 권한 문제(권한 승인 전에는 장치 라벨이 빈 문자열로 옴)를 겪었나?
> 장치 전환 시 기존 peer connection의 트랙을 어떻게 갈아끼웠나 (`replaceTrack`?)
> — 겪었다면 이건 좋은 면접 소재다. 코드를 열어서 확인하고 적을 것.

## 6. 포즈 인식 안정화 (단독)

`81fcba3`, `d63063a`, `0cf044f` — `Fe/fix/mediapipe` 커밋 3개 (2026-08-03 ~ 08-04).
`resolvePosePoints.ts` 136줄 중 **89줄(65%)** 이 내 코드다.

플레이어 관절이 **그대로 게임 지형이 되는** 구조라, 관절 떨림과 미인식이 곧 게임 물리 오류였다.
세 가지를 했다:

1. **속도 적응형 EMA 스무딩** — 프레임 간 이동거리로 분기해, 정지 시엔 알파 0.65로 떨림을 잡고
   빠른 동작(화면 폭 4% 이상 이동) 시엔 0.95로 지연 없이 추종
2. **결측 관절 freeze 전략** — 안 잡힌 관절은 이전 유효 좌표를 유지.
   "인접 관절로 대체" 방식은 손목이 팔꿈치로 순간이동하는 문제가 있어 제거
3. **모델 및 임계값 튜닝** — `pose_landmarker_lite` → `full`,
   detection/presence/tracking 신뢰도를 0.35/0.7/0.5로 역할별 분리

중간에 **가려진 관절을 `[0,0]`으로 초기화했다가 다리가 화면 좌상단으로 찢어지는 버그를 만들고 22분 만에 되돌린** 과정이 있다.

## 협업 방식

- **브랜치 전략**: `fe/feat/*`, `fe/fix/*`, `be/*` 접두사 + MR 머지 (master 직접 푸시 없음)
- **커밋 규칙**: `[FE]feat:`, `[BE]fix:` 형식이 팀 규칙이었으나 **내 커밋 상당수가 이를 안 지켰다**
  (`Fe/fix/mediapipe` = 브랜치명 그대로). 이 문서를 쓰면서 그 대가를 직접 치렀다.
- **CI**: MR마다 validate → test 자동 실행, master 머지 시 EC2 자동 배포
- **도구**: GitLab (이슈·MR), Jira (스프린트), Notion (문서)
